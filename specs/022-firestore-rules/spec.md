# Spec 022: Firestore 보안 규칙 강화

- 상태: Implementing  <!-- Draft → Ready → Implementing → Verified -->
- 최종 수정일: 2026-11-26
- 제품 문서: [docs/product.md](../../docs/product.md) 기능 022
- 디자인 자료: 없음 — 화면 변화 없음(5절 생략)

> 이 문서는 **무엇을, 왜** 만드는지만 적는다. 기술 선택·파일 구조는 plan.md에 쓴다.
> 모르는 것은 추측하지 말고 `[확인 필요: …]`로 남긴다. `/sdd-clarify`가 이 표시를 찾아 질문한다.

## 1. 문제와 목표

자체 서버가 없어서(DEC-001) 사용자 데이터를 지키는 수단은 Firestore 보안 규칙뿐이다. 그런데 저장소의 `firestore.rules`는 로그인한 사람이면 누구나 다른 사용자의 게임 데이터와 랭킹 문서를 쓰고 지울 수 있게 되어 있다. 또 전광판은 코드와 규칙의 컬렉션 이름이 달라 규칙상 동작할 수 없다. 이 기능이 끝나면 다음이 성립해야 한다.

- 사용자는 자기 문서만 바꿀 수 있다.
- 지금 쓰는 기능(저장, 랭킹, 전광판, 탈퇴)은 그대로 동작한다.
- 운영 콘솔에 배포된 규칙이 저장소 파일과 같다는 것이 기록으로 남는다.

## 2. 범위

- 포함:
  - `nmixx_tcg_users`: 문서 읽기·쓰기·삭제를 그 문서의 주인에게만 허용한다. `nmixx_tcg_leaderboard`: 읽기는 공개, 쓰기·삭제는 주인에게만 허용한다.
  - 전광판: 규칙과 코드가 같은 컬렉션 이름을 쓰게 한다.
  - `nmixx_tcg_market`: 숨김 기능이므로 쓰기를 모두 막는다.
  - 규칙에 없는 컬렉션은 모두 거부한다.
  - 운영 콘솔 배포본과 저장소 `firestore.rules`가 같은지 확인하고, 배포 절차를 기록한다(product.md Q-01).
  - 강화한 규칙에 막히는 기존 클라이언트 요청을 정리한다. 랭킹 조회 중 다른 사용자의 문서를 덮어쓰는 코드(DEC-023 위반, AC-07)와, 다른 사용자의 `nmixx_tcg_users`를 읽는 닉네임 중복 확인·교환소 프로필 조회(AC-03b)가 여기에 해당한다.
- 제외:
  - 재화·컬렉션 값이 정당한지 서버에서 검증하는 일(조작 방지) — 서버 로직이 필요해 DEC-001 범위 밖이다. 따로 결정한다.
  - 카카오 사용자의 Firebase 인증 연동 자체를 구현하는 일 — 별도 기능으로 명세한다. 이 기능의 규칙은 연동보다 먼저 운영에 배포했다(2026-11-26, DEC-028, REQ-05).
  - 동시 저장 충돌 병합(DEC-011).
  - 숨김 기능(015 더스트, 016 교환소)을 다시 여는 일.
- 선행 조건:
  - Firebase 프로젝트 `nmixx-tcg` 콘솔(Firestore 규칙 화면)에 접근할 수 있는 권한
  - 기능 007(로그인), 008(저장), 010(랭킹), 011(전광판), 014(탈퇴)
  - 카카오 사용자가 클라우드 저장을 다시 쓰려면: 카카오 로그인 사용자가 Firebase 인증을 받은 상태로 Firestore에 요청하는 기능(별도 명세, 미작성 — DEC-027 계약)

## 3. 사용자 흐름

이 기능은 사용자 화면을 바꾸지 않는다. 바뀌는 것은 Firestore가 요청을 받아들이는지 거부하는지다.

1. 구글 로그인 사용자가 팩을 열면 자기 `nmixx_tcg_users` 문서와 랭킹 문서가 지금처럼 저장된다.
2. 고등급 카드를 뽑으면 전광판에 올라가고, 다른 사용자 화면에도 보인다.
3. 누군가 개발자도구로 다른 사용자의 문서를 쓰거나 지우려 하면 Firestore가 거부하고, 대상 문서는 그대로 남는다.
4. 탈퇴하면 자기 문서만 지워진다.
5. 규칙 배포 후 저장·랭킹·전광판이 실패하면, 운영자는 직전 규칙으로 되돌리고 원인을 기록한다(AC-17).

## 4. 요구사항과 인수 조건(AC)

> 용어: **문서 주인** — 문서 ID가 가리키는 계정. 계정 ID는 `goog_<Firebase uid>`, `kakao_<카카오 회원번호>` 형식이다(DEC-008). Firebase 인증 uid와 문서 ID가 **같지 않으므로**, 주인 판단은 이 접두어를 고려해야 한다.
> 아래 AC는 Firestore 에뮬레이터 또는 콘솔의 규칙 시뮬레이터에서 요청이 허용·거부되는지, 그리고 운영 데이터에서 문서가 남는지로 확인한다. 확인 방법은 plan.md에서 정한다.

### REQ-01: 사용자 게임 데이터는 주인만 쓴다

`nmixx_tcg_users/{id}` 문서를 읽거나, 만들거나, 고치거나, 지우는 일은 그 문서의 주인만 할 수 있다. 이 문서에는 이메일과 전체 컬렉션이 들어 있기 때문이다(Q-A). 다른 사용자의 공개 정보(닉네임, 아바타, 수집 수)가 필요한 기능은 랭킹 문서(`nmixx_tcg_leaderboard`, 이메일 없음)만 읽는다. 해당 기능은 닉네임 중복 확인(기능 013)과 교환소 상대 프로필 조회(기능 016)다.

- **AC-01** 정상: 본인 저장
  - Given 구글 로그인 사용자 A(문서 `goog_A`)
  - When 팩을 열어 게임 상태가 저장된다
  - Then `nmixx_tcg_users/goog_A`의 `collection`·`coins`·`lastSavedAt`이 새 값으로 바뀌고, 콘솔에 권한 오류가 없다
- **AC-02** 권한 오류: 타인 문서 쓰기
  - Given 구글 로그인 사용자 A, 다른 사용자 B의 문서 `goog_B`
  - When A의 인증으로 `nmixx_tcg_users/goog_B`에 `coins`를 쓰려 한다
  - Then 요청이 `permission-denied`로 거부되고, `goog_B`의 모든 필드가 그대로다
- **AC-03** 권한 오류: 타인 문서 삭제·비로그인 쓰기
  - Given 문서 `goog_B`가 있다
  - When (가) A가 지우려 하거나, (나) 로그인하지 않은 요청이 쓰려 한다
  - Then 두 경우 모두 거부되고 문서가 남는다
- **AC-03a** 권한 오류: 타인 문서 읽기
  - Given 사용자 A, 다른 사용자 B의 문서 `goog_B`(이메일 포함)
  - When A가 `goog_B`를 직접 읽거나, `nmixx_tcg_users` 전체를 대상으로 검색(예: 닉네임 일치)하려 한다
  - Then 두 요청 모두 거부되고 A의 화면·콘솔 어디에도 B의 이메일이 나타나지 않는다
- **AC-03b** 정상: 닉네임 중복 확인
  - Given 랭킹 문서에 닉네임 `엔써123`인 사용자 B가 있다
  - When A가 프로필에서 닉네임을 `엔써123`으로 바꾸려 한다
  - Then 이미 쓰는 닉네임이라는 안내가 보이고 A의 닉네임은 바뀌지 않는다. 권한 오류 때문에 확인이 실패하는 경우는 없다
- **AC-03c** 경계: 랭킹 문서가 없는 사용자와의 중복
  - Given 사용자 문서는 있지만 랭킹 문서가 없는 사용자 C의 닉네임이 `엔써777`이다
  - When A가 닉네임을 `엔써777`로 바꾼다
  - Then 변경이 허용된다(알려진 한계: 랭킹에 오르지 않은 사용자와는 닉네임이 겹칠 수 있다)
- **AC-04** 정상: 본인 탈퇴
  - Given 구글 로그인 사용자 A
  - When 정보 탭에서 회원 탈퇴를 실행한다(기능 014)
  - Then `nmixx_tcg_users/goog_A`와 `nmixx_tcg_leaderboard/goog_A`가 사라지고, 다른 사용자 문서는 하나도 바뀌지 않는다

### REQ-02: 랭킹 문서는 누구나 읽고, 주인만 쓴다

`nmixx_tcg_leaderboard/{id}`는 로그인하지 않은 방문자도 읽을 수 있다(기능 010). 만들기·고치기·지우기는 주인만 할 수 있다.

- **AC-05** 정상: 랭킹 읽기와 본인 등록
  - Given 로그인하지 않은 방문자, 구글 로그인 사용자 A
  - When 방문자가 랭킹 탭을 열고, A가 팩을 연다
  - Then 방문자 화면에 Top 50이 보이고, `nmixx_tcg_leaderboard/goog_A`의 `uniqueCardCount`가 갱신된다
- **AC-06** 권한 오류: 타인 랭킹 조작
  - Given 사용자 A, 랭킹 문서 `goog_B`
  - When A가 `goog_B`의 `uniqueCardCount`를 바꾸거나 문서를 지우려 한다
  - Then 거부되고 `goog_B`가 그대로다
- **AC-07** 회귀: 조회 중 타인 문서 쓰기 없음
  - Given 랭킹 문서의 `displayName`에 `박민주`가 들어 있는 다른 사용자 B가 있다(현재 코드는 조회 중 B의 문서를 `anjffhrkwl`로 덮어쓰려 한다)
  - When A가 랭킹 탭을 연다
  - Then 랭킹 화면에 B가 `anjffhrkwl`로 표시된다. A의 클라이언트는 B의 `nmixx_tcg_users`·`nmixx_tcg_leaderboard` 문서에 쓰기 요청을 보내지 않는다(네트워크 기록에 해당 쓰기가 없음). B의 문서 값은 그대로다
  - 참고: 로그인·닉네임 저장 때 본인 문서에 적용하는 같은 치환(`sanitizeDisplayName`)은 바꾸지 않는다

### REQ-03: 전광판은 규칙과 코드가 같은 컬렉션을 쓴다

전광판(기능 011)은 하나의 컬렉션 이름으로 통일한다. 누구나 읽을 수 있고, 로그인 사용자는 새 항목을 **추가만** 할 수 있다. 기존 항목은 고치거나 지울 수 없다.

- **AC-08** 정상: 고등급 획득이 전광판에 오른다
  - Given 구글 로그인 사용자 A가 운영 규칙이 적용된 상태에 있다
  - When 전광판 대상 등급 카드를 뽑는다
  - Then 전광판 컬렉션에 A의 항목이 하나 추가되고, 다른 브라우저의 방문자 화면에 그 항목이 보인다
- **AC-09** 권한 오류: 전광판 위조·삭제
  - Given 전광판에 다른 사용자의 항목이 있다
  - When A가 그 항목을 고치거나 지우려 하거나, 로그인하지 않은 요청이 항목을 추가하려 한다
  - Then 모두 거부되고 전광판 내용이 그대로다
- **AC-10** 경계: 추가 항목의 작성자
  - Given 사용자 A
  - When 작성자 uid를 B(`goog_B`)로 적은 항목을 추가하려 한다
  - Then 거부되고 전광판에 B 이름의 항목이 생기지 않는다. 작성자 uid가 `goog_A`이면 표시 이름이 무엇이든 허용된다

### REQ-04: 숨김 상태인 교환소는 쓰기를 모두 막는다

교환소(기능 016)는 메뉴에서 숨겨져 있지만(DEC-022) 컬렉션과 코드는 남아 있다. 숨김 기능에 쓰기 구멍을 남기지 않도록, `nmixx_tcg_market`의 등록·수정·삭제를 누구에게도 허용하지 않는다(Q-B). 기존 등록글은 지우지 않고 그대로 두며, 읽기는 지금처럼 누구나 할 수 있다. 교환소를 다시 열 때는 권한을 새로 설계한다(`/sdd-change`로 016 갱신).

- **AC-11** 권한 오류: 새 등록 거부
  - Given 구글 로그인 사용자 A
  - When `nmixx_tcg_market`에 등록글을 만들려 한다(판매자를 본인으로 적어도)
  - Then 거부되고 컬렉션에 새 문서가 생기지 않는다
- **AC-12** 권한 오류: 기존 등록글 수정·삭제 거부
  - Given 기존 등록글(본인 것이든 남의 것이든)
  - When A가 내용이나 `status`를 바꾸거나 지우려 한다(현재 코드의 구매자 완료 처리 포함)
  - Then 모두 거부되고 등록글이 그대로다
- **AC-13** 정상: 기존 등록글 보존과 읽기
  - Given 규칙 배포 전에 등록글이 있었다
  - When 배포 후 로그인하지 않은 요청이 등록글을 읽는다
  - Then 읽기가 허용되고, 등록글 수가 배포 전과 같다

### REQ-05: 카카오 사용자도 본인 문서를 계속 쓸 수 있다

지금 카카오 로그인은 Firebase 인증을 거치지 않는다(DEC-008). 그래서 Firestore 입장에서는 카카오 사용자의 요청과 로그인하지 않은 요청이 구별되지 않는다. 이 상태에서 REQ-01~03을 적용하면 카카오 사용자의 저장·랭킹 등록·전광판 추가가 모두 거부된다. 원래는 카카오 연동 뒤에 배포하기로 했지만(DEC-026), 운영 규칙에서 누구나 남의 데이터를 바꿀 수 있음이 확인되어 **먼저 배포했다**(2026-11-26, DEC-028). 카카오 연동이 나올 때까지 카카오 사용자는 로컬 저장만 쓴다. 카카오 사용자의 문서 주인 판단은 구글과 같은 기준을 따른다. 문서 `kakao_<회원번호>`의 주인은 그 카카오 계정으로 인증된 요청이다.

- **AC-14** 사전 확인: 현재 운영 상태 기록
  - Given 운영 콘솔의 현재 Firestore 규칙
  - When 규칙을 바꾸기 전에 배포본을 저장소 파일과 비교하고, 운영 데이터에서 `kakao_` 문서의 최근 `lastSavedAt`을 확인한다
  - Then 비교 결과(같음/다름과 차이), 카카오 저장이 실제로 되고 있는지가 product.md Q-01·Q-02에 날짜와 함께 기록된다
- **AC-15** 정상: 카카오 사용자 본인 저장
  - Given 카카오 인증 연동과 새 규칙이 모두 운영에 배포되었고, 카카오 로그인 사용자 K(문서 `kakao_K`)가 있다
  - When K가 팩을 연다
  - Then `nmixx_tcg_users/kakao_K`와 `nmixx_tcg_leaderboard/kakao_K`가 갱신되고, 전광판 대상 카드면 전광판에 K의 항목이 추가된다
- **AC-15a** 권한 오류: 카카오 사용자의 타인 문서 쓰기
  - Given 카카오 사용자 K, 다른 사용자의 문서 `goog_A`·`kakao_J`
  - When K가 그 문서들에 쓰려 한다
  - Then 거부되고 대상 문서가 그대로다
- **AC-15b** (DEC-028로 변경) 배포 순서 기록
  - Given 카카오 인증 연동보다 규칙을 먼저 배포했다
  - When 배포를 기록한다
  - Then DEC-028에 이유, 카카오 사용자가 잃는 기능, 되돌리는 방법이 적혀 있다

### REQ-06: 배포와 되돌리기

저장소의 `firestore.rules`가 운영 규칙의 원본이다. 배포 방법과 되돌리는 방법이 기록되어 있어야 한다.

- **AC-16** 정상: 배포 후 일치
  - Given 이 기능의 규칙이 저장소에 반영되었다
  - When 운영에 배포한다
  - Then 콘솔 규칙 화면의 내용이 저장소 파일과 같고, 배포 날짜와 커밋이 product.md 또는 decisions.md에 기록된다
- **AC-17** 실패·복구: 배포 후 기능 고장
  - Given 새 규칙을 배포한 직후
  - When 구글 사용자의 저장(AC-01), 랭킹 읽기(AC-05), 전광판(AC-08) 중 하나라도 실패한다
  - Then 운영자가 콘솔의 규칙 이력에서 직전 버전으로 되돌릴 수 있고, 되돌린 뒤 해당 기능이 다시 동작한다. 실패 내용이 기록된다
- **AC-18** 기본 거부: 목록에 없는 컬렉션
  - Given 규칙에 정의하지 않은 컬렉션 이름(예: `nmixx_tcg_unknown`)
  - When 로그인 사용자가 읽거나 쓰려 한다
  - Then 거부된다

## 6. 품질 요구

- 권한: 조회 경로에서 다른 사용자의 문서를 쓰거나 지우지 않는다(DEC-023). 규칙이 이를 강제한다.
- 개인정보: `nmixx_tcg_users` 문서에는 이메일이 들어 있으므로 주인만 읽는다(AC-03a). 공개 문서인 랭킹 문서에는 이메일을 넣지 않는다.
- 운영 데이터 보호: 검증은 에뮬레이터·시뮬레이터에서 먼저 한다. 운영 데이터로 하는 확인은 테스트 계정 문서로만 한다(`npm run dev`도 운영 Firestore에 연결됨).

- Q-A 해결(2026-11-25): `nmixx_tcg_users`는 주인만 읽는다. 닉네임 중복 확인과 교환소 프로필은 랭킹 문서를 쓰고, 랭킹에 없는 사용자와 닉네임이 겹칠 수 있는 한계는 받아들인다. REQ-01, AC-03a·03b·03c에 반영했다. 교환소의 상대 컬렉션 조회(`fetchUserCollection`)는 대체할 공개 데이터가 없어 동작하지 않게 된다. 처리는 Q-B와 함께 정한다.
