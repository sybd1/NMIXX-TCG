요청: $ARGUMENTS

- 작업 ID가 없으면 대상 tasks(또는 Lite spec의 작업 절)에서 체크되지 않은 첫 작업을 한다.
- `all`이면 작업을 순서대로 하나씩 끝까지 진행하되, 작업마다 아래 절차를 모두 지키고 실패나 막힘이 생기면 멈춘다.
- 대상 폴더가 없으면 `specs/`에서 상태가 Verified가 아닌 폴더 중 번호가 가장 큰 것을 쓴다.

## 시작 전 확인

- spec(Full이면 plan·tasks도)이 `Ready` 또는 `Implementing`이 아니면 멈추고 이유를 알린다.
- 이 작업의 선행 작업이 끝났는지 확인한다.
- 처음 시작하는 작업이면 문서 상태를 `Implementing`으로 바꾼다.

## 절차

1. spec, plan, 이 작업에 연결된 AC와 plan 6절의 테스트 정의, 관련 코드를 읽는다.
2. **테스트 작업**이면: 테스트를 작성하고 실행해 **실패**하는 것을 확인한다. 실패 이유가 "기능이 없어서"인지 확인한다(문법 오류·잘못된 import로 인한 실패는 안 됨).
3. **구현 작업**이면: 연결된 테스트를 통과하는 최소한의 코드를 쓴다. `CLAUDE.md`의 코딩 규칙과 기존 구조를 따른다.
4. 완료 기준의 명령을 실행하고, 관련 기존 테스트가 깨지지 않았는지 확인한다.
5. 통과하면 tasks의 체크박스를 체크한다. 실패하면 체크하지 않고 원인을 기록한다.

## 지킬 것

- 이 작업 범위 밖의 기능, 리팩터링, 의존성 추가를 하지 않는다.
- 테스트를 통과시키려고 테스트나 AC를 고치지 않는다. 테스트가 틀렸다고 판단되면 멈추고 근거를 보고한다.
- 명세대로 구현할 수 없으면(계약 충돌, 라이브러리 제약 등) 코드로 우회하지 말고 멈춘다. 원인과 필요한 결정, 고쳐야 할 문서를 보고한다.
- 구현 중 확정한 세부사항(오류 문구, 기본값 등)은 spec·plan에 반영한다.

## 끝나면 보고

- 변경한 파일
- 실행한 명령과 결과 (통과·실패를 출력 근거와 함께)
- 충족한 AC, 남은 작업
- 다음 작업 ID 또는 `/sdd-verify`
