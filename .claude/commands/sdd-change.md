변경 요청: $ARGUMENTS

## 절차

1. 관련 spec·plan·tasks, `docs/decisions.md`, 관련 코드를 읽는다. 대상 기능이 분명하지 않으면 후보를 보여주고 묻는다.
2. **영향 분석** — 현재 명세와 변경 요청을 비교해 정리한다.
   - 바뀌는 사용자 동작, 추가·수정·삭제되는 AC
   - 바뀌는 계약(필드, 타입, 상태 코드, 오류 코드)과 기존 데이터에 미치는 영향
   - 다른 기능(spec)에 미치는 영향
   - 다시 검증해야 할 AC
3. 영향이 크거나(계약 변경, 데이터 마이그레이션, 다른 기능 영향) 해석이 둘 이상이면, 문서를 고치기 전에 분석 결과를 보여주고 확인을 받는다.
4. **문서 갱신** — spec → plan → tasks 순서로 고친다.
   - 바뀐 AC는 ID를 유지하고 내용을 고친다. 삭제한 AC는 지우지 말고 `~~취소선~~`과 이유를 남긴다. 새 AC는 다음 번호를 쓴다.
   - tasks에 변경 작업을 추가하고, 재검증할 AC의 판정을 `미실행`으로 되돌린다.
   - 문서 상태를 `Ready`로 되돌린다(Verified였다면 포함).
5. 계약·정책·구조가 바뀌면 `docs/decisions.md`에 새 결정을 추가하고, 대체된 결정의 상태를 바꾼다.

## 끝나면 보고

- 영향 분석 요약
- 고친 문서와 바뀐 AC
- 추가한 작업과 재검증할 AC
- 다음 단계: `/sdd-implement`

소스 코드는 수정하지 않는다.
