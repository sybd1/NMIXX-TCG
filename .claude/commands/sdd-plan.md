대상: $ARGUMENTS (비어 있으면 `specs/`에서 상태가 Verified가 아닌 폴더 중 번호가 가장 큰 것)

## 시작 전 확인

- `spec.md`에 구현을 막는 `[확인 필요]`가 있으면 멈추고 `/sdd-clarify`를 먼저 하라고 알린다.
- Lite 트랙이면 plan.md를 만들지 않는다. 필요하면 Full로 전환할지 묻는다.

## 절차

1. `CLAUDE.md`, `docs/decisions.md`, `spec.md`를 읽는다.
2. 관련 소스 코드를 **직접 열어** 구조, 재사용할 요소, 기존 계약·오류 형식, 테스트 방식을 확인한다.
3. `specs/_templates/full/plan.md`를 복사해 채운다.
   - 1절에는 실제로 열어본 경로만 적는다.
   - 3절 계약은 프로젝트 언어의 타입·스키마 코드로 쓴다. 이미 계약 파일이 있거나 만들 예정이면 원본 위치를 하나로 정한다.
   - 6절에서 spec의 **모든** AC를 테스트에 연결한다. 기존 테스트 도구로 할 수 없는 것만 수동 절차로 둔다.
   - 새 의존성은 이유와 대안을 쓰고 `docs/decisions.md`에 제안 상태로 기록한다.
4. 설계 중 spec에 빈틈이나 모순을 발견하면 plan에 덮어쓰지 말고 spec을 고치거나 `[확인 필요]`로 남긴다.

## 끝나면 보고

- 핵심 설계 요약 (구조, 계약 위치, 새 의존성)
- 6절 표에 연결되지 않은 AC (있으면 이유)
- 사용자가 결정해야 할 항목
- 다음 단계: `/sdd-tasks`

소스 코드는 수정하지 않는다.
