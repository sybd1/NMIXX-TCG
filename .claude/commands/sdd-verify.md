대상: $ARGUMENTS (비어 있으면 `specs/`에서 상태가 Verified가 아닌 폴더 중 번호가 가장 큰 것)

## 절차

1. spec, plan(Full), tasks(또는 Lite spec의 작업·검증 절)를 읽는다.
2. **AC별 검증** — plan 6절(Lite는 구현 메모의 테스트)에 정의된 방법으로 각 AC를 확인한다.
   - 자동 테스트: 해당 테스트를 실행하고 출력을 근거로 남긴다.
   - 수동 절차: 앱을 실행해 절차대로 확인할 수 있으면 직접 하고 관찰 내용을 적는다. 할 수 없으면 `실행 불가`와 이유를 적는다.
   - 정상 흐름만이 아니라 입력 오류, 빈 상태, 요청 실패와 복구도 spec의 AC대로 확인한다.
3. **프로젝트 검사** — `CLAUDE.md`의 테스트 전체, 타입·린트, 빌드 명령을 실행한다.
4. **영향 확인** — 이번 변경이 건드린 기존 흐름을 확인한다.
5. **문서·코드 일치 확인** — 구현 결과가 spec·plan과 다르면 어느 쪽이 맞는지 구분한다.
   - 코드 오류면 수정하고 해당 AC를 다시 확인한다.
   - 명세 누락·변경이면 수정하지 말고 보고한다(`/sdd-change` 대상).
6. 검증 기록 표와 프로젝트 검사 표를 채운다. 판정은 `통과 / 실패 / 미실행 / 실행 불가(사유)` 중 하나다.
7. 모든 작업이 체크되고, 모든 AC가 `통과`이고, 프로젝트 검사가 통과한 경우에만 spec·plan·tasks와 `docs/product.md`의 상태를 `Verified`로 바꾼다.

## 지킬 것

- 실행하지 않은 검증을 통과로 적지 않는다. 출력이나 관찰 근거가 없으면 통과가 아니다.
- 실패를 감추려고 테스트를 건너뛰거나(`skip`, `only`) 기준을 낮추지 않는다.

## 끝나면 보고

- AC별 판정 표
- 프로젝트 검사 결과
- 고친 것, 남은 실패와 원인
- 최종 상태 (Verified 여부와 이유)
